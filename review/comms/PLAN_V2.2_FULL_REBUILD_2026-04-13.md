# v2.2 Full Rebuild Plan

## 0. Why this replaces the earlier v2.2 plan

Three problems converged:

1. **Action sequence corruption.** Owner found at least 5 of 40
   facing-bet test set hands had invalid action sequences (e.g.
   BB bets, CO bets, action jumps to BB skipping BTN). Owner did
   not review the remaining hands. The 351 training situations were
   generated by the same pipeline — they are suspect.

2. **LLM agents cannot reliably find sequence errors.** Owner
   tested this directly. Agents tasked with reviewing sequences
   missed errors that the owner found by reading. A deterministic
   tool is required.

3. **The RAISE tree retirement + hand-bucket-first labelling.**
   All existing labels were produced under the sequential tree
   approach. Owner has approved Option A: relabel everything.

These three issues compound. We cannot relabel situations that have
corrupt sequences. We cannot trust sequences that haven't been
validated by the tool. Therefore: **reconstruct sequences, validate,
relabel the valid ones, compare old vs new, then retrain.**

## 1. The key insight: reconstruct, don't discard

### Owner direction

Keep the same hero cards, boards, positions, and streets from the
existing 351 situations. Reconstruct valid action sequences from the
available data. Relabel with bucket-first. Compare old labels
against new labels on the same hands.

### Why this is better than regenerating from scratch

1. **Comparison data.** Same hand + different label = we can see
   exactly where the bucket-first approach disagrees with the old
   sequential approach. This is the safety net — if bucket-first
   produces something wrong on a hand where the old label was
   clearly right, we catch it.

2. **Isolation of variables.** When cards/board/positions stay the
   same, any label change is caused by either (a) the sequence
   correction fixing wrong features, or (b) the bucket-first
   reasoning reaching a different conclusion. We can trace which.

3. **No coverage gap.** The existing 351 situations span a designed
   tactical space. Regenerating randomly might miss corners that
   the original allocation deliberately covered.

### What we have to reconstruct from

| Source | Count | Cards/board? | Sequence data available |
|---|---|---|---|
| Self-play (`d####`) | 200 (3-way) | Yes | `prior_actions`: hero-only free-text (`"flop: CO check"`). Plus feature counters: `villain_aggression_count`, `villain_checked_back`, `villain_call_count`, `num_callers_to_bet`, `facing_bet`, `facing_raise` |
| Factory (`_Board`) | 151 (2-way) | Yes | No `prior_actions`. But: `facing_bet`, `villain_aggression_count`, `villain_checked_back`, `pot`, `to_call`. 2-way sequences are highly constrained — usually one valid sequence |

### Phase 1: Reconstruct and validate existing situations

**Goal:** For each of the 351 existing situations, reconstruct the
action sequence from available data, validate it, and classify the
result. Keep the same cards, board, positions, and street.

#### Step 1.1 — Build the sequence reconstruction tool

**Who:** Architect (design) → Programmer (build + test)

The tool takes a situation record and produces all valid action
sequences consistent with its feature values. It works differently
for the two data sources:

**Factory situations (151, 2-way):**

With only 2 players, the sequence is highly constrained. The tool
uses:
- `hero_position`, `villain_positions` → who acts and in what order
- `facing_bet` → whether villain bet before hero's decision point
- `villain_aggression_count` → how many bets/raises villain made
- `villain_checked_back` → whether villain checked when they could
  have bet
- `pot`, `to_call` → constrains bet sizing

For most 2-way spots, exactly one valid sequence produces the
observed feature values. The tool enumerates candidates and runs
each through `hand_sequence_validator`.

**Self-play situations (200, 3-way):**

With 3 players, there are more possible sequences. The tool uses:
- `prior_actions` (hero-only, e.g. `"flop: CO check"`) → hero's
  actions on prior streets
- `hero_position`, `villain_positions` → position order
- `facing_bet`, `facing_raise` → what hero faces at decision point
- `villain_aggression_count` → total villain bets/raises this street
- `villain_checked_back` → villain had opportunity to bet but
  checked
- `villain_call_count` → how many villain calls on this street
- `num_callers_to_bet` → how many players called a bet before hero

The tool enumerates candidate sequences that produce the observed
feature values and validates each through `hand_sequence_validator`.

**Output per situation — one of three classifications:**

| Classification | Meaning | Action |
|---|---|---|
| **CERTAIN** | Exactly 1 valid sequence produces the observed features | Attach the sequence. Features are trustworthy. |
| **AMBIGUOUS** | Multiple valid sequences produce the observed features | Attach any valid sequence (features are consistent regardless). Flag for review if the ambiguity affects labelling-relevant features. |
| **CORRUPT** | Zero valid sequences produce the observed features | The features are impossible under any legal action order. This situation's features — and therefore its label — cannot be trusted. |

**Tests:** The tool must include:
- Unit tests for 2-way reconstruction (known valid, known corrupt)
- Unit tests for 3-way reconstruction (known valid, known ambiguous,
  known corrupt)
- A self-consistency check: for any CERTAIN/AMBIGUOUS result, re-
  extract features from the reconstructed sequence and confirm they
  match the original feature values

**Gate:** Tool passes all tests. Reviewed by owner before running
on the full dataset.

#### Step 1.2 — Run reconstruction on all 351 situations

**Who:** Programmer

Run the tool on every situation in `3way_combined_350.jsonl`.
Produce a classification report:

```
CERTAIN:   N situations (action string attached, features verified)
AMBIGUOUS: N situations (valid sequence attached, ambiguity noted)
CORRUPT:   N situations (no valid sequence exists)
```

For each CORRUPT situation, report:
- situation_id
- what features are inconsistent
- what the validator rejects (specific error message)

**Gate:** Classification report reviewed by owner.

#### Step 1.3 — Handle CORRUPT situations

**Who:** Programmer (generation) + Owner (review)

For each CORRUPT situation, regenerate it through the hardened
factory pipeline using the **same cards, board, hero position,
villain positions, and street**. The factory produces a new
situation with:
- A valid, validated action sequence
- Correct features extracted from the valid sequence
- The `action_string` field populated

The regenerated situation replaces the corrupt one. It has the
same poker hand but a correct action sequence, which may produce
different feature values (because the original features were
derived from a corrupt sequence).

If the factory cannot produce a valid situation with the same
cards/board/positions (e.g. card conflicts), document why and
replace with a new situation that fills the same tactical slot
(same street, same position, same expected action type).

**Gate:** All 351 situations now have validated action strings.
Zero CORRUPT situations remain. Feature audit: all 48 features
non-NULL across all situations.

#### Step 1.4 — Re-extract features for all situations

**Who:** Programmer

Run the feature extractor on all 351 situations using their
validated action strings. This produces:
- Correct values for all sequence-derived features
  (`villain_aggression_count`, `villain_checked_back`, etc.)
- Populated values for previously-NULL features
  (`flush_block_pct`, `flush_draw_rank`, `hero_range_percentile`)

Produce a feature diff report: for each situation, which feature
values changed from the original? Large changes on CERTAIN
situations indicate a feature extraction bug (the sequence was
valid but features were wrong). Large changes on formerly-CORRUPT
situations are expected.

**Gate:** Feature diff report reviewed by owner.

#### Step 1.5 — Small-scale validation

**Who:** Programmer + Owner

Before running labelling on 351 situations, pick 10 situations
(5 CERTAIN, 3 AMBIGUOUS, 2 formerly-CORRUPT) and walk through
end-to-end:
- Reconstructed sequence is correct
- Features extracted from the sequence are correct
- The situation reads like a real poker hand

**Gate:** Owner confirms 10 samples look right.

#### Step 1.6 — Owner review of Phase 1

**Gate:** Approve reconstructed dataset before labelling begins.

**The comparison report (Step 2.6) is the key deliverable:**

```
situation_id | old_action | new_action | agree? | sequence_status | feature_changes | hand_bucket | strategic_role
d0244_CO_r   | CALL       | CALL       | YES    | CERTAIN         | none            | medium_made | mandatory_defend
d4211_BTN_t  | FOLD       | FOLD       | YES    | CERTAIN         | none            | weak_made   | equity_denial
FB_Board3_h4 | RAISE      | RAISE      | YES    | CORRUPT→regen   | 3 features      | strong_made | value_bet
d1822_BB_f   | CALL       | RAISE      | NO     | CERTAIN         | none            | drawing     | semi_bluff
...
```

**What the comparison tells us:**

| Old | New | Sequence | What it means |
|---|---|---|---|
| Same | Same | CERTAIN | Both approaches agree on a valid hand. High confidence. |
| Same | Same | CORRUPT→regen | Agreement even after fixing the sequence. Good sign. |
| Different | — | CERTAIN | Sequence was fine. The bucket-first reasoning reached a different conclusion. Review individually — is the new label better? |
| Different | — | CORRUPT→regen | Sequence was broken AND reasoning changed. The old label was built on corrupt data with a weaker method. New label is almost certainly better, but verify. |
| Same | Same | AMBIGUOUS | Agreement despite sequence ambiguity. Features were consistent regardless of sequence. Trustworthy. |

**Disagreement analysis:**
- If overall disagreement is < 10%: bucket-first is largely
  consistent with the old approach. The changes are targeted
  improvements (likely RAISE corrections and passive bias fixes).
- If disagreement is 10-25%: significant shift. Review all
  disagreements individually. Most should be explainable as
  bias corrections.
- If disagreement is > 25%: one of the approaches is badly
  wrong. Stop and diagnose before proceeding.

## 7. Risk register

| Risk | Likelihood | Mitigation |
|---|---|---|
| Reconstruction tool produces mostly AMBIGUOUS for 3-way | Medium | Even AMBIGUOUS is safe — features are consistent regardless of which valid sequence produced them. Only CORRUPT situations need replacement. |
| High CORRUPT rate (>30%) makes comparison less useful | Low-Medium | If many situations are corrupt, the comparison still works for the non-corrupt ones. Corrupt situations are replaced with same cards/board, so we still get partial comparison (same hand, different sequence + different label). |
| Bucket-first disagreement rate > 25% | Low | Stop and diagnose. Review a sample of disagreements with owner. Likely means one approach is systematically wrong — but that's exactly what the comparison is designed to catch. |
| Feature re-extraction changes values on CERTAIN situations | Low | Would indicate a feature extractor bug (valid sequence, different features). Investigate before proceeding — this is a pipeline bug, not a labelling issue. |
| Reconstruction tool is complex to build | Medium | Phase 1.1 has an explicit design step and owner review. Start with 2-way (simpler, 151 situations) before tackling 3-way. If 3-way reconstruction is too ambiguous, fall back to regenerating 3-way situations via factory with same cards/board. |
| New model regresses despite better data | Medium | Regression gate at 82.5% is hard. Comparison report lets us diagnose whether regression comes from label changes or feature changes. |
| Regenerated CORRUPT situations have different feature distributions | Low | Expected — the original features were wrong. The comparison report tracks feature changes explicitly so we can see the impact. |
